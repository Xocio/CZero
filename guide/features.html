功能详解 ​

CZero 的每项功能都可在 config.json 中单独开关，并按各自的计划自动触发。本页说明每个功能做什么、什么时候做、有哪些保护。逐字段的取值见配置参考。

缓存清理 ​

为高频应用（微信、QQ、抖音）提供各自独立的清理器，按 app_clean.detect_schedule 的频率触发。

触发前的检测 ​

每次触发前会先看应用当前的状态，避免无谓或有害的清理：

  • 前台应用不清理 —— 应用正处于前台使用时，本轮跳过，避免影响正在进行的操作。
  • 游戏前台保护 —— 前台为游戏时不执行清理。

每个应用的开关 ​

json
"wechat": { "enabled": true, "enhanced": false }
  • enabled —— 是否清理该应用。
  • enhanced —— 增强模式。开启后清理范围更广，默认关闭以求稳妥。

其他应用清理 ​

app_clean.other 处理三大应用之外的缓存，按其 schedule 定时执行（默认每天 03:00）。

总开关与时序屏障 ​

  • 受总开关 general.auto_clean 控制。
  • 受 general.temporal_barrier_days（时序屏障）保护：只清理 N 天以前的文件，保护近期数据；设为 0 表示不启用。

后台压制 ​

按 suppress.detect_schedule 的频率，周期性结束目标应用在后台的进程，释放内存、减少后台耗电。

  • 只动子进程 —— 主进程不受影响，通知与消息推送照常。
  • 前台应用绝不动 —— 正在前台的应用不会被压制；本轮识别不出前台应用时也会跳过，避免误伤。
  • 名单可改 —— 默认针对 微信 / QQ / 支付宝，可在 CZeroX 里增删应用、按应用单独启停。

F2FS 垃圾回收 ​

在存储空闲吃紧时触发 F2FS 垃圾回收（GC），把碎片化的空间整理出来。

GC 是磁盘密集操作，所以只在设备真正空闲时才动手。以下任一条不满足都会跳过本轮：

条件字段默认
存储确实需要回收free_percent / target_percent空闲比例低于 95% 才触发，回到 98% 即完成
屏幕必须是熄灭的wait_screen_off_timeout最多等 30 秒，到点仍亮屏就放弃
距上次回收的间隔min_interval_hours6 小时
必须在充电require_charging关（不要求）
非充电时的最低电量min_battery40%
电池温度上限max_battery_temp40.0°C

另有 max_runtime_sec 限制单次最长运行时长，到时强制停止。

长期观察不到执行属于正常

准入条件较为严格，且系统自身正在执行维护时 CZero 会主动让路。若连续数次回收收效甚微，间隔还会自动拉长，避免无谓的重复尝试。

GC 功能需要 /data 为 F2FS 分区。非 F2FS 设备可将 gc.enabled 设为 false，其余功能不受影响。

fstrim ​

trim 是独立于 GC 的一项任务（默认每 7 天 04:00 一次），把已释放的空间告知底层存储，让 UFS / eMMC 自己的垃圾回收有据可依，长期有助于维持写入性能。

  • 调度与 GC 完全独立，也不受 gc.enabled 影响。
  • 同样要求息屏；屏幕亮着则本轮跳过。

别把周期调得太密

fstrim 对存储器件有实际写入压力，默认的每周一次已经足够，不建议改成每天。

精细化压制 ​

上面的后台压制是直接把后台进程结束掉；精细化压制是它的温和版本 —— 压制而不杀死：应用被挂起后不再消耗 CPU，但内存里的状态完整保留，切回去瞬间就恢复，不用重新加载。

这套能力由 Android 系统本身提供，模块不代劳执行，只负责在开机时把它调到可用状态：

字段做什么
auto_enable每次开机打开系统的精细化压制能力
disable_vendor_guard关掉厂商自研的保活/压制，避免两套策略互相打架

参与压制的应用名单在 CZeroX 里管理，不写进 config.json。

两者如何选择

可以并存。后台压制适用于结束后无副作用、常驻仅占内存的子进程；精细化压制适用于希望保留运行现场、但不允许其在后台活动的应用。

需要 Android 12+

更低版本上这两个开关不会生效。

空文件夹清理 ​

按 empty_folder.schedule 定时清扫残留的空目录（默认每天 04:00）。清扫范围与白名单都可以在 CZeroX 里编辑，规则按分组组织，可整组启停。

自定义路径清理 ​

除内置规则外，你可以声明自己的清理路径，由每日任务统一清扫，同时用白名单保护不想被碰的目录。两者都在 CZeroX 的规则编辑器里管理，重装模块时会被继承。

规则支持通配符，也会自动去重（父目录已在列表里时，其下的子路径不重复处理），白名单的优先级始终更高。

除了按路径分组的规则，还有一份按应用组织的规则表：在 CZeroX 的「应用缓存」页里可以按应用查看各路径的实际占用、逐条增删，也可以从云端共享库拉取别人验证过的规则。两份规则在清理时合并处理，行为完全一致。

你也可以订阅第三方规则源，添加后每天自动更新一次。

清理并非直接删除，而是先移入回收站（见下节），默认保留 7 天，期间可完整恢复。

回收站与恢复 ​

为避免误删无法挽回，其他 / 自定义路径清理不做真正的删除，而是把命中的文件移动到回收站保存一段时间，确认无碍后才随过期自动清除。

  • 移动而非删除 —— 被清理的文件按原目录结构保存，可以原样恢复回原位，包括符号链接。
  • 按次归档 —— 每次清理单独成一组记录，可以看到这次清了哪些文件、多大、什么时候过期。
  • 默认保留 7 天 —— 可用 general.recycle_keep_days 调整（缺省或填 0 即 7 天）。过期后自动清除。
  • 不被相册扫描 —— 移进去的图片 / 视频不会出现在媒体库里。
  • 保留修改时间 —— 恢复后不会被时序屏障误判为"新文件"。
  • 回收站自我保护 —— 清理规则即使匹配到内置存储根目录，也永远不会清理回收站自身。

回收站位于内置存储的 Recycle 文件夹，日常通过 CZeroX 的回收站页面查看与恢复即可。

统计与日志 ​

  • 统计 —— 各应用的清理次数、压制次数与释放空间都会累计，并保留近 90 天的每日历史，CZeroX 的「清理趋势」页据此画柱状图。每天 00:00 结转当日计数，关机跨过 0 点也不会漏。
  • 日志 —— 开启 general.log 后，所有组件写入同一份每日日志，每条带来源标签（[定时] [检测] [微信] [压制] [GC] [空文件夹] [自定义] 等），便于区分是哪个环节产生的。日志只保留当天。

两者默认关闭，可随时开启或关闭。

超级岛通知 ​

清理开始与结束时会通知 CZeroX，在应用侧显示执行进度 / 结果（含超级岛）。由 general.notification 控制。
