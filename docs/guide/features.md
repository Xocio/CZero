# 功能详解

CZero 的每项功能都可在 `config.json` 中单独开关，并按各自的计划自动触发。本页说明每个功能**做什么、什么时候做、有哪些保护**。逐字段的取值见[配置参考](/guide/configuration)。

## 缓存清理

为高频应用（微信、QQ、抖音）提供各自独立的清理器，按 `app_clean.detect_schedule` 的频率触发。

### 触发前的检测

每次触发前会先看应用当前的状态，避免无谓或有害的清理：

- **前台应用不清理** —— 应用正处于前台使用时，本轮跳过，避免影响正在进行的操作。
- **游戏前台保护** —— 前台为游戏时不执行清理。

### 每个应用的开关

```json
"wechat": { "enabled": true }
```

- `enabled` —— 是否清理该应用。

微信、QQ 与抖音的清理同样覆盖应用双开（分身）下的数据。

::: tip 增强模式已移除
早期版本中的「增强模式」已下线；旧配置里残留的 `enhanced` 字段不再生效，升级后会被自动清除。
:::

### 清理间隔

`app_clean.min_interval_hours`（默认 12 小时）限定**同一应用两次自动清理之间的最小间隔**。检测频率只决定多久判断一次，是否真正清理还需满足该间隔，因此在频繁切换应用时不会反复触发清理，也避免无谓的耗电与卡顿。修改后即时生效。

### 其他应用清理

`app_clean.other` 处理三大应用之外的缓存，按其 `schedule` 定时执行（默认每天 03:00）。

### 总开关与时序屏障

- 受总开关 `general.auto_clean` 控制。
- 受 `general.temporal_barrier_days`（**时序屏障**）保护：只清理 N 天以前的文件，保护近期数据；设为 `0` 表示不启用。

## 后台压制

按 `suppress.detect_schedule` 的频率，周期性结束目标应用在后台的进程，释放内存、减少后台耗电。

- **只动子进程** —— 主进程不受影响，通知与消息推送照常。
- **前台应用绝不动** —— 正在前台的应用不会被压制；本轮识别不出前台应用时也会跳过，避免误伤。
- **低开销** —— 检测过程不会每轮重新拉起进程，也不频繁查询窗口与电源状态，对流畅度与续航的影响很小。
- **名单可改** —— 默认针对 微信 / QQ / 支付宝，可在 CZeroX 里增删应用、按应用单独启停。

## F2FS 垃圾回收

在存储空闲吃紧时触发 F2FS 垃圾回收（GC），把碎片化的空间整理出来。

GC 是磁盘密集操作，所以只在设备真正空闲时才动手。以下任一条不满足都会跳过本轮：

| 条件 | 字段 | 默认 |
|---|---|---|
| 存储确实需要回收 | `free_percent` / `target_percent` | 空闲比例低于 95% 才触发，回到 98% 即完成 |
| 屏幕必须是熄灭的 | `wait_screen_off_timeout` | 最多等 30 秒，到点仍亮屏就放弃 |
| 距上次回收的间隔 | `min_interval_hours` | 6 小时 |
| 必须在充电 | `require_charging` | 关（不要求） |
| 非充电时的最低电量 | `min_battery` | 40% |
| 电池温度上限 | `max_battery_temp` | 40.0°C |

另有 `max_runtime_sec` 限制单次最长运行时长，到时强制停止；回收过程中屏幕一旦亮起，会立即停止高强度回收。

::: tip 长期观察不到执行属于正常
准入条件较为严格，且系统自身正在执行维护时 CZero 会主动让路。若连续数次回收收效甚微，间隔还会自动拉长，避免无谓的重复尝试。
:::

> GC 功能需要 `/data` 为 F2FS 分区。非 F2FS 设备可将 `gc.enabled` 设为 `false`，其余功能不受影响。

::: tip Shizuku 版
Shizuku 版没有模块自带的回收方案，改由系统的空闲维护完成，上表中的触发条件不适用，也没有对应的设置项。详见[版本选择](/guide/editions)。
:::

## fstrim

`trim` 是独立于 GC 的一项任务（默认每 7 天 04:00 一次），把已释放的空间告知底层存储，让 UFS / eMMC 自己的垃圾回收有据可依，长期有助于维持写入性能。

- 调度与 GC **完全独立**，也不受 `gc.enabled` 影响。
- 同样要求息屏；屏幕亮着则本轮跳过。

::: warning 别把周期调得太密
fstrim 对存储器件有实际写入压力，默认的每周一次已经足够，不建议改成每天。
:::

## 精细化压制

::: info 仅 Root 版
该功能依赖系统框架，Shizuku 版不提供。
:::

上面的[后台压制](#后台压制)是直接把后台进程结束掉；**精细化压制**是它的温和版本 —— **压制而不杀死**：应用退到后台后被挂起，不再占用 CPU、不运行后台任务，但内存里的状态完整保留，切回去瞬间恢复，不用重新加载。

::: warning BETA
该功能目前处于 BETA 阶段，个别设备上可能出现压制失效等情况。若检测到上次启用期间系统运行异常，会自动关闭并给出提示，重新开启即可。
:::

### 使用前提

- Android 12 及以上，且内核支持应用冻结；更低版本上该功能不会生效。
- 已安装 LSPosed，并在其中为 CZeroX 勾选**系统框架**作用域；未勾选时相关开关均不起作用。
- 开启后需重启手机一次才开始生效。

### 压制名单

首次使用时会默认纳入一批应用（即时通讯、音乐、导航类除外），可在 CZeroX 的压制应用名单中按需增删。被压制期间应用收不到推送，因此不建议加入即时通讯、音乐与导航类应用。输入法、桌面、拨号、短信等系统关键应用会被强制排除，无法加入。

### 生效检测

CZeroX 的**生效检测**页会实际冻结一次测试进程，并逐项检查框架 Hook、冻结器与厂商限制是否真正生效，便于确认该功能在当前设备上能否使用。检测未通过时，可通过「请求适配我的设备」打包设备信息发送给开发者。

### 厂商限制与开机动作

已适配 Android 17 与 HyperOS 4 的厂商冻结限制。`config.json` 的 `freezer` 一节控制开机阶段的相关动作：

| 字段 | 做什么 |
|---|---|
| `auto_enable` | 每次开机打开系统的精细化压制能力 |
| `disable_vendor_guard` | 关掉厂商自研的保活/压制，避免两套策略互相打架 |

参与压制的应用名单在 CZeroX 里管理，不写进 `config.json`。

::: tip 两者如何选择
可以并存。后台压制适用于结束后无副作用、常驻仅占内存的子进程；精细化压制适用于希望保留运行现场、但不允许其在后台活动的应用。
:::

## 空文件夹清理

按 `empty_folder.schedule` 定时清扫残留的空目录（默认每天 04:00）。清扫范围与白名单都可以在 CZeroX 里编辑，规则按分组组织，可整组启停。

清扫时有以下保护：

- 不会删除系统为应用创建的目录，避免应用随后写入文件失败；
- 不会进入其他挂载目录与符号链接；
- 微信、抖音默认已加入保护白名单。

## 自定义路径清理

除内置规则外，你可以声明自己的清理路径，由每日任务统一清扫，同时用白名单保护不想被碰的目录。两者都在 CZeroX 的规则编辑器里管理，重装模块时会被继承。

规则支持通配符，也会自动去重（父目录已在列表里时，其下的子路径不重复处理），白名单的优先级始终更高。白名单按完整路径层级匹配，较短、较通用的条目不会误伤名称相近的其他目录；也可以在白名单的「选择应用」页中一键添加应用。

除了按路径分组的规则，还有一份**按应用组织**的规则表：在 CZeroX 的「应用缓存」页里可以按应用查看各路径的实际占用、逐条增删，也可以从云端共享库拉取别人验证过的规则。两份规则在清理时合并处理，行为完全一致。

你也可以订阅第三方[规则源](/guide/rule-source)，添加后每天自动更新一次。

清理并非直接删除，而是先移入回收站（见下节），默认保留 7 天，期间可完整恢复。

## 回收站与恢复

为避免误删无法挽回，其他 / 自定义路径清理**不做真正的删除**，而是把命中的文件**移动到回收站**保存一段时间，确认无碍后才随过期自动清除。

- **移动而非删除** —— 被清理的文件按原目录结构保存，可以**原样恢复回原位**，包括符号链接。
- **按次归档** —— 每次清理单独成一组记录，可以看到这次清了哪些文件、多大、什么时候过期。
- **默认保留 7 天** —— 可用 `general.recycle_keep_days` 调整（缺省或填 `0` 即 7 天），仅影响之后新产生的记录。过期后自动清除。
- **可以关闭** —— 通过 `general.recycle_enabled` 或 CZeroX 的回收站设置关闭后，清理将直接彻底删除，无法恢复，请谨慎。
- **不被相册扫描** —— 移进去的图片 / 视频不会出现在媒体库里。
- **保留修改时间** —— 恢复后不会被时序屏障误判为"新文件"。
- **回收站自我保护** —— 清理规则即使匹配到内置存储根目录，也永远不会清理回收站自身。

回收站位于内置存储的 `Recycle` 文件夹，日常通过 CZeroX 的回收站页面查看与恢复即可。

## 文件归类

自动整理下载目录等位置里散落的文件：按类型移入统一的分类目录。该功能默认关闭，在 CZeroX 的文件归类页开启；也可随时手动「立即归类」。

- **来源目录** —— 需要整理的目录，可一键添加常用位置（下载目录、浏览器与下载工具、聊天工具、网盘、图片与媒体等），其中风险较高的位置会标注「谨慎」。
- **归类目录与分类** —— 默认归入内置存储的 `CZero` 文件夹，分为安装包、压缩包、文档、图片、视频、音频、脚本、字体与其他；各分类的目录名可自定义，也可设为「不归类」而保留在原处，并可一键切换全部目录名的语言。
- **扫描深度** —— 可仅处理来源目录本身，或向下处理若干层 / 不限层级；目录本身不会被移动。
- **归类延迟** —— 文件写入完成后静置一段时间再移动（默认 60 秒），避免移动尚未稳定的文件；连续到达的文件会一并处理。
- **重复文件** —— 可将同名且同大小的文件移入单独的重复目录，而非追加序号。
- **安装包重命名** —— 可在归类后按应用名命名安装包。
- **自动跳过** —— 未完成的下载（`.crdownload`、`.part` 等）与刚写入的文件不会被处理；未完成的下载会在概览中单独列出，可安全删除。
- **完整还原** —— 归类历史按日期记录每次移动，可整日还原，也可勾选部分文件还原；文件列表支持缩略图预览、直接分享与精确到秒的时间显示。

对应 `config.json` 的 `file_sort` 一节，字段见[配置参考](/guide/configuration#file-sort)。

::: tip 版本差异
Root 版的文件归类已正式提供，免费使用；Shizuku 版中该功能仍处于 BETA 阶段，且为捐赠解锁功能。
:::

首次使用建议先从下载目录开始，并在「确认归类」预览中核对待移动的文件。

## 垃圾扫描

CZeroX 主页的垃圾扫描卡片按**当前生效的清理规则**统计各路径的实际占用，并给出可清理总量与分项详情。扫描过程为只读，不会删除任何内容。

## Zero 智能助手

Zero 是 CZeroX 内的对话式助手，需自行填写模型服务的 API 密钥（支持 OpenAI 兼容与 Anthropic 兼容接口）。它可以扫描存储、预估清理可释放的空间、浏览目录并将其转为自定义规则、管理应用压制、检查模块运行状况与读取清理历史。

- **操作先确认** —— 任何会更改设备的操作，都会先给出确认卡片，确认后才执行。
- **后台持续** —— 离开应用后对话仍会继续，可通过通知（支持超级岛）查看进度并确认或取消。
- **会话管理** —— 对话按会话保存，自动命名，可回看或删除。

该功能为捐赠解锁功能，目前处于 BETA 阶段。

## 统计与日志

- **统计** —— 各应用的清理次数、压制次数与释放空间都会累计，并保留近 90 天的每日历史，CZeroX 的「清理趋势」页（捐赠解锁）据此画柱状图。每天 00:00 结转当日计数，关机跨过 0 点也不会漏。
- **日志** —— 开启 `general.log` 后，所有组件写入同一份每日日志，每条带来源标签（`[定时]` `[检测]` `[微信]` `[压制]` `[GC]` `[空文件夹]` `[自定义]` `[归类]` 等），便于区分是哪个环节产生的。日志只保留当天。

两者默认关闭，可随时开启或关闭。

## 超级岛通知

清理开始与结束时会通知 CZeroX，在应用侧显示执行进度 / 结果（含超级岛）。由 `general.notification` 控制，空文件夹清理与检测的通知同样遵守该开关。
