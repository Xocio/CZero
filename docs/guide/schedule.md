# 调度模型

`config.json` 里所有调度都用同一个对象表达：

```json
"schedule": { "every": "<ISO8601 时长>", "at": "<HH:MM>" }
```

- **`every`** —— ISO8601 时长，表示"每隔多久"。
- **`at`** —— 可选，`HH:MM`（24 小时制，补零），表示一天中的执行时刻。**仅当周期 ≥ 1 天时有意义**。

模块直接读取 `config.json` 换算出调度，没有任何中间派生文件，也不需要你接触 cron 表达式。

## `every` 的取值规则

| 含义 | `every` 写法 | 是否需要 `at` |
|---|---|---|
| 每 N 分钟 | `PT2M`（每 2 分钟） | 否 |
| 每 N 小时 | `PT4H`（每 4 小时） | 否 |
| 每 N 天 | `P1D` / `P3D` | **是**（指定几点执行） |
| 每 N 周 | `P1W` / `P2W` | **是** |

格式固定：

- `PT<正整数>M` / `PT<正整数>H` —— 时间分量（分 / 时）。
- `P<正整数>D` / `P<正整数>W` —— 日期分量（天 / 周）。

数字必须是 **≥ 1 的正整数**，并且分钟不能超过 **59**、小时不能超过 **23** —— 因为它们最终要落进一分钟一格、一小时一格的位图里，`PT90M` 这种写法无法表达，会被判为无效调度而跳过。想要"每 90 分钟"请改用 `PT1H` 或 `PT2H`。

## 两类调度

| 类型 | 字段 | 特点 |
|---|---|---|
| **频率类** | `app_clean.detect_schedule`、`suppress.detect_schedule`、`gc.schedule` | 只用分钟 / 小时间隔，**不写 `at`** |
| **定时类** | `app_clean.other.schedule`、`empty_folder.schedule`、`trim.schedule` | 既有间隔（每几天 / 几周），又有时刻 `at` |

::: tip 间隔不是从"上次执行"起算
分钟 / 小时间隔是**对齐到整点**的：`PT4H` 表示在 0、4、8、12、16、20 点各跑一次，而不是"距上次 4 小时"。分钟同理，`PT5M` 落在 0、5、10… 分。
:::

## 对照示例

| `every` / `at` | 含义 |
|---|---|
| `PT2M` | 每 2 分钟 |
| `PT4H` | 每 4 小时 |
| `P1D` + `03:00` | 每天 03:00 |
| `P3D` + `03:00` | 每 3 天的 03:00 |
| `P1W` + `04:00` | 每周一次，04:00 |

## 关键约束

::: warning 务必遵守
1. **频率类不要写 `at`**（写了会被忽略）；**定时类（天 / 周）必须写 `at`**，否则默认按 `00:00` 执行。
2. **`every` 必须是 ≥ 1 的正整数**，且分钟 ≤ 59、小时 ≤ 23。解析失败时该任务会被跳过，等于该功能不执行 —— 日志里会有一条「无效调度」记录。
3. **写完即生效，无需重启** —— 请用原子写入（先写临时文件再 `mv` 覆盖）。
:::

## 几点补充说明

- **多天周期是按实际间隔计算的**，而非"每天到点就跑"。设备关机或跨过执行时刻不会导致任务被漏掉，恢复后会在下一个时刻补上。
- **休眠错过的任务会补执行一次**，同一任务仅补一次，不会因错过数小时而连续执行多轮。
- **`gc.schedule` 不等于 GC 的执行频率**。它只决定多久检查一次，是否真正执行还需满足 `gc.min_interval_hours` 及其他准入条件，因此调密该值并不会让 GC 更频繁地运行。
- **统计结转与日志清理**固定在每天 00:00 执行，不由 `config.json` 控制。
